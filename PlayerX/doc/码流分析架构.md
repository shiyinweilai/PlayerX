# PlayerX 码流分析模块架构（务实版）

## 0. 背景与目标

前一版方案（"终极/ 行业顶配"）把自研 CABAC/CAVLC 熵解码引擎、VVC 全语法、HRD 完整仿真、CTU 四叉树重建都列为一期必须实现，**在真实编解码工程背景下不成立**，原因：

1. **CABAC/CAVLC 上下文建模极其复杂**（H.264/HEVC 各自数千个上下文变量，随标准修订持续变化），从零自研且要与标准解码器结果位对齐，工作量相当于重写一个解码器核心，性价比极低。
2. **FFmpeg 已经在做这件事**——本项目已经把完整 FFmpeg 源码 vendor 进仓库（`PlayerX/ffmpeg/`），`libavcodec` 里的 h264/hevc 解码器在解码过程中**内部已经算出**了 QP-per-MB、CU/PU 划分、运动矢量、参考帧列表等信息，只是没有通过公开 API 导出。现实做法是**给自带的解码器源码打补丁导出这些内部字段**，而不是另起一套熵解码器去重新算一遍。
3. **VVC**：FFmpeg 的 `libavcodec/vvc` 解码器成熟度和调试信息覆盖度都远不如 h264/hevc，且业务上暂无 VVC 素材，不适合作为一期目标，列入远期预留。
4. **HRD**：真正的编码器 HRD 仿真需要编码器侧的私有参数配合，分析工具做不到"仿真"，能做到的是"**基于 SPS/VUI 里声明的 HRD 参数，对实际码流做越限估算/告警**"，文档措辞要如实。
5. VMAF 依赖 `libvmaf` 第三方库，不是 FFmpeg 自带，属于新增依赖，需要单独评估，不放进一期范围。

本方案在这些约束下，按照 `rb_demuxer.h` / `rb_decoder.h` 已有的分层与命名风格（纯 C++ 核心用 `RB` 前缀类名 + `rbXxx()` 方法名，Qt 桥接层参照 `EngineBridge` / `YuvBridge` 风格）重新设计，分阶段落地。

---

## 1. 整体分层

沿用现有播放引擎的分层习惯：底层复用 `RBDemuxer`，中间新增一层纯 C++ 语法解析/统计层，顶层用一个 Qt 桥接类暴露给 QML，UI 遵循 `doc/主题.md` 的弹层规范。

```
┌───────────────────────────────┐
│      QML 码流分析 UI 层        │  时序视图 / NAL 树 / QP热力图 / 码率曲线
└───────────────┬───────────────┘
                │ Q_PROPERTY / Q_INVOKABLE / signals
┌───────────────┴───────────────┐
│   RBStreamBridge（Qt 桥接层）  │  多 slot 管理、异步调度、QVariant 转换
└───────────────┬───────────────┘
                │ 纯 C++ 结构体，无 Qt 类型
┌───────────────┴───────────────┐
│  RBStreamAnalyzer（分析引擎层） │  GOP/POC 重建、码率统计、HRD 估算、块级信息聚合
└───────────────┬───────────────┘
                │ RBNalUnit / RBSpsInfo / RBFrameSyntax / RBBlockInfo
┌───────────────┴───────────────┐
│ RBBitstreamParser（轻量语法层） │  NAL 分割、SPS/PPS/SEI/Slice Header 关键字段解析
└───────────────┬───────────────┘
                │ AVPacket（裸包，不解码）
┌───────────────┴───────────────┐
│      RBDemuxer（已存在，复用）  │  文件打开、AVPacket 遍历、时间戳
└───────────────┬───────────────┘
                │ 需要块级信息时，走下面这条"补丁导出"支路
┌───────────────┴───────────────┐
│ 自带 FFmpeg 解码器（打补丁导出） │  QP/CU划分/MV 等内部调试数据，经 RBDecoder 扩展获取
└───────────────────────────────┘
```

关键说明：**语法解析（NAL/SPS/PPS/Slice Header）和"块级深度信息（QP/CU/MV）"是两条不同难度的路径**，不能混为一谈：

- 前者只需要按标准把 bit 一个个读出来，字段量有限（分辨率、profile/level、POC 相关参数、slice_type、qp_delta 等），**自己写一个轻量 bit reader 完全可行**，不涉及熵解码。
- 后者（CU 划分、MV、逐块 QP）藏在 CABAC 熵解码结果里，只能靠解码器算出来。现实路径是扩展 `RBDecoder`，在其内部解码调用后，从打过补丁的 `AVCodecContext`/私有结构里把这些字段透出（见 §4）。

## 2. 数据模型（RB 前缀，纯 C++，无 Qt 依赖）

```cpp
namespace rb {

// ── 语法层输出（RBBitstreamParser）──────────────────────────────
struct RBNalUnit {
    int      type      = 0;      // nal_unit_type
    int64_t  offset     = 0;      // 在文件/包中的字节偏移
    int      size        = 0;
    bool     isAnnexB    = true;  // AnnexB(0x000001) / AVCC(长度前缀) 识别结果
};

struct RBSpsInfo {
    int  profile = 0, level = 0;
    int  width = 0, height = 0;
    int  maxNumRefFrames = 0;
    int  pocType = 0;             // pic_order_cnt_type（POC 推导依据）
    bool hrdPresent = false;
    // HRD 相关（仅解析 SPS/VUI 里声明的参数，用于估算，不做完整仿真）
    int  cpbSizeBits = 0;
    int  bitRateBits = 0;
};

struct RBPpsInfo {
    int  initQp = 0;
    bool entropyCodingModeCabac = true; // false=CAVLC（仅 H.264）
    bool deblockingEnabled = true;
};

struct RBSliceHeaderInfo {
    int      sliceType = 0;       // I/P/B
    int      qpDelta   = 0;
    int64_t  pocLsb    = 0;       // 用于 POC 重建，非完整语法
};

// ── 分析引擎层输出（RBStreamAnalyzer）───────────────────────────
enum class RBFrameType { IDR, I, P, B, SKIP, Unknown };

struct RBFrameInfo {
    int64_t      packetIndex = 0;
    double       pts = 0.0, dts = 0.0;
    int64_t      poc = 0;          // 重建后的显示序号
    RBFrameType  type = RBFrameType::Unknown;
    int          sizeBytes = 0;
    double       avgQp = 0.0;      // 依赖 §4 的补丁数据，取不到则为 -1
};

struct RBGopInfo {
    int64_t startFrameIndex = 0;
    int     frameCount = 0;
    bool    isOpenGop = false;     // 依据首帧是否可独立解码判断
};

// HRD 估算结果（基于 SPS 声明参数，非真实仿真）
struct RBHrdEstimate {
    double cpbOccupancyPeakRatio = 0.0; // 估算峰值占用 / 声明 CPB 容量
    bool   overflowRisk = false;
    bool   underflowRisk = false;
};

// ── 块级深度信息（需 §4 补丁支持，取不到时整体不返回该结构）──────
struct RBBlockInfo {
    int   x = 0, y = 0, w = 0, h = 0;  // CU/CTU 位置与尺寸
    int   qp = 0;
    bool  isSkip = false;
    bool  isIntra = true;
    float mvx = 0.f, mvy = 0.f;        // 帧间块运动矢量（帧内块为 0）
};

} // namespace rb
```

## 3. 核心类（纯 C++，命名对齐 `rb_decoder.h` / `rb_demuxer.h`）

```cpp
namespace rb {

// 轻量语法解析：NAL 分割 + SPS/PPS/SEI/SliceHeader 关键字段
// 只做 bit 级读取，不做熵解码，适用范围见 §0 第 1/2 点
class RBBitstreamParser {
public:
    bool rbFeedPacket(const uint8_t* data, int size, bool isAvcc);
    std::vector<RBNalUnit> rbLastNalUnits() const;
    bool rbParseSps(const RBNalUnit&, RBSpsInfo& out) const;
    bool rbParsePps(const RBNalUnit&, RBPpsInfo& out) const;
    bool rbParseSliceHeader(const RBNalUnit&, const RBSpsInfo&, RBSliceHeaderInfo& out) const;
};

// 分析引擎：时序/GOP/码率/HRD 估算/块级信息聚合，纯 C++ 无 Qt
class RBStreamAnalyzer {
public:
    bool rbOpen(const std::string& filePath);   // 内部持有一个 RBDemuxer 做预扫描
    void rbClose();

    // 预扫描：只读包头+语法层，不解码，得到全片时序骨架
    bool rbPrescan();
    int  rbFrameCount() const;
    const RBFrameInfo& rbFrameAt(int index) const;
    std::vector<RBGopInfo> rbGopList() const;
    RBHrdEstimate rbHrdEstimate() const;

    // 惰性块级解析：仅在用户查看某一帧时才触发解码 + 补丁数据读取
    // 取不到补丁数据（例如非 h264/hevc 或解码器未打补丁）时返回空 vector
    std::vector<RBBlockInfo> rbBlockInfoAt(int frameIndex);

private:
    RBBitstreamParser m_parser;
    std::unique_ptr<RBDemuxer> m_demuxer;   // 复用已有 RBDemuxer 做包遍历
    std::unique_ptr<RBDecoder> m_decoder;   // 仅块级信息需要时才启用解码
    std::vector<RBFrameInfo>   m_frames;
    // LRU 缓存最近查看过的帧的块级信息，避免重复解码
};

} // namespace rb
```

约束（对齐现有 `RBDemuxer`/`RBDecoder` 的边界原则）：
- `RBBitstreamParser` / `RBStreamAnalyzer` **不引入任何 Qt 类型**，可独立编译成命令行工具用于离线排查。
- `RBStreamAnalyzer` 通过持有 `RBDemuxer`/`RBDecoder`（已有类）复用现成的解封装/解码能力，**不重复实现**。
- 预扫描阶段只读包大小/时间戳/NAL 类型，**不解码**；块级信息按帧惰性触发，避免打开大文件时卡顿。

## 4. 块级深度信息的现实获取方式（重点）

这是与"终极版"最大的路线差异，必须明确写清楚，避免后续被当成"自研熄entropy decoder"来验收：

1. 在 `PlayerX/ffmpeg/libavcodec/` 对应解码器（h264dec.c / hevcdec.c）里，**给已有的宏块/CU 解析函数打补丁**：在其内部循环里，把已经算出来的 QP、划分尺寸、预测模式、MV 写入一个新增的 side data（例如自定义 `AV_FRAME_DATA_RB_BLOCK_INFO`），随 `AVFrame` 一起吐出来。
2. `RBDecoder` 增加一个可选接口（不影响现有播放路径）：解码完成后检查该帧是否带有 `RB_BLOCK_INFO` side data，有则转换为 `std::vector<RBBlockInfo>` 交给上层。
3. 这样做的好处：**复用了解码器已验证的熵解码结果**，不需要自己对齐标准；补丁只是"多导出几个已经算好的变量"，改动量和维护成本远小于自研 CABAC。
4. 局限：只支持 FFmpeg 已支持且被我们打过补丁的编码格式（先做 H.264/HEVC，AVC 优先），VVC/AV1 待 FFmpeg 相应解码器成熟后再评估。

## 5. Qt 桥接层：`RBStreamBridge`

参照 `YuvBridge.h` / `EngineBridge.h` 已有风格（`Q_PROPERTY` + `Q_INVOKABLE` + `signals`，多 slot 管理），新增一个不侵入现有播放/YUV 模块的独立桥接类：

```cpp
class RBStreamBridge : public QObject {
    Q_OBJECT
    Q_PROPERTY(int  slotCount   READ slotCount   NOTIFY slotCountChanged)
    Q_PROPERTY(bool prescanning READ prescanning  NOTIFY prescanningChanged)

public:
    static constexpr int MaxSlots = 9; // 与 YuvBridge 一致，支持多路对比

    Q_INVOKABLE int  openFile(const QString& path);
    Q_INVOKABLE void closeSlot(int slot);

    // 时序/GOP/码率 一次性拿全量（预扫描完成后调用，量级：帧数 * 小结构体）
    Q_INVOKABLE QVariantList frameList(int slot) const;
    Q_INVOKABLE QVariantList gopList(int slot) const;
    Q_INVOKABLE QVariantMap  hrdEstimate(int slot) const;

    // 块级信息：按帧惰性获取，返回空数组代表当前格式/文件不支持
    Q_INVOKABLE QVariantList blockInfoAt(int slot, int frameIndex) const;

    // 联动播放器 seek（复用 EngineBridge，不重复实现）
    Q_INVOKABLE void seekPlayerTo(int slot, int frameIndex);

signals:
    void slotCountChanged();
    void prescanningChanged();
    void prescanProgress(int slot, double ratio); // 大文件预扫描进度条
    void frameReady(int slot, int frameIndex);    // 块级信息异步就绪
};
```

- 预扫描放在后台线程（复用 `RBDemuxer` 读包不解码的特性，速度足够快），扫描进度通过 `prescanProgress` 上报，避免打开大文件卡 UI。
- 块级解析（需要解码）默认异步执行，完成后发 `frameReady`，QML 侧再拉取 `blockInfoAt`，避免主线程卡顿。

## 6. UI 层

复用现有 QML 弹层规范（见 `doc/主题.md`：Popup + ListView 自绘，禁止 `Menu` 自定义样式，配色统一 `#cc1a1a1f` / `#e8e8ec` / hover `#0a64f0`）。一期只做以下几个视图，不铺开全部 9 个模块：

1. **StreamInfoPanel**：容器/SPS/PPS 关键参数、profile/level、分辨率、HDR 基础字段。
2. **FrameTimelineView**：I/P/B 帧色块时间轴，点击联动播放器 seek（`seekPlayerTo`）。
3. **BitrateChartView**：瞬时/平均码率曲线 + HRD 估算越限提示（不叫"HRD 曲线视图"，避免暗示做了真实仿真）。
4. **QpHeatmapView**：块级 QP 热力图，仅当 `blockInfoAt` 返回非空时可用，否则显示"该格式暂不支持块级分析"。

## 7. 分阶段路线（务实版，替代"不考虑成本"的说法）

| 阶段 | 内容 | 依赖 |
|---|---|---|
| P0 | `RBBitstreamParser`（NAL 分割、SPS/PPS 关键字段）+ `RBStreamAnalyzer` 预扫描（帧类型/POC/GOP/码率统计）+ `RBStreamBridge` 基础接口 + StreamInfoPanel/FrameTimelineView/BitrateChartView | 仅需复用现有 `RBDemuxer`，无需改 FFmpeg 源码 |
| P1 | HRD 估算（基于 SPS/VUI 声明参数）、H.264/HEVC 解码器打补丁导出块级信息、`RBDecoder` 扩展、QpHeatmapView | 需要修改 `PlayerX/ffmpeg/libavcodec` 源码并重新编译 FFmpeg |
| P2（远期，视需要评估） | 运动信息/残差可视化（复用 P1 补丁里已导出的 MV/残差字段）、画质评估（引入 `libvmaf` 依赖或先只做已有 YUV 模块的 PSNR/SSIM）、VVC 支持（待 FFmpeg VVC 解码器成熟） | 新增第三方依赖，需单独立项评估 |

## 8. 依赖边界

1. `RBBitstreamParser` / `RBStreamAnalyzer` 不引入 Qt 类型，可独立编译；`RBStreamBridge` 是唯一 Qt 依赖层，只做数据转换和调度，不含分析逻辑（与 `YuvBridge` 的职责划分保持一致）。
2. 块级深度信息完全依赖"自带 FFmpeg 解码器打补丁导出"，**不做独立于 FFmpeg 的熵解码重实现**；升级 FFmpeg 版本时需要重新对齐补丁位置，这是本方案唯一的长期维护成本，需在补丁代码里写清楚对应的上游函数名/行为，方便升级时重新定位。
3. 预扫描与块级惰性解析分离，避免大文件打开卡顿；块级信息按 LRU 缓存，淘汰长时间未查看的帧。
4. 多路码流对比复用 `RBStreamBridge` 的多 slot 设计（与 `YuvBridge` 一致），每路独立 `RBStreamAnalyzer` 实例，互不影响。
